# Using Sherpa and UFO models for simulating BSM phyiscs

Sherpa has the ability to include extensions of the Standard Model (SM) formulated in UFO (Universal Feynrules Output) models generated by the FeynRules package (References: [FeynRules](https://arxiv.org/abs/0806.4194), [A comprehensive approach to new physics simulations](https://arxiv.org/abs/0906.2474), [UFO 2.0](https://arxiv.org/abs/2304.09883)). For general information on the use of UFO models in Sherpa, please reference the relevant section in the [Sherpa manual](https://sherpa-team.gitlab.io/sherpa/master/manual/parameters/models.html).

ATLAS maintains a collection of UFO models, originally intended for the use in Madgraph. It can be found on [Gitlab](https://gitlab.cern.ch/atlas-generators-team/MadGraphModels) or under `/cvmfs/atlas.cern.ch/repo/sw/Generators/madgraph/models/latest/`. In order for Sherpa to be able to use the UFO model, it needs to first be compiled into a library. 

## Compiling the UFO model into a library
The UFO model written in Python needs to be translated into C++ code, which is then compiled into a library. In a Sherpa installation with an enabled UFO interface this is handled by a script called `Sherpa-generate-model`. Make sure that you have a copy of the model directory in a place where you have writing access. Then run the model generation with the command 

`Sherpa-generate-model <path-to-ufo-model> --auto_convert --install_dir=$PWD`.

Depending on the complexity of the UFO model, its compilation may take a little bit of time and a considerable amount of memory, so if you are using a cluster of some sort it might be necessary to provide enough resources.

Running the script will produce several things:
* A compiled library (`libSherpa<model_name>.so`)
* An example configuration file (`Sherpa_<model_name>.yaml`) that shows what new settings are available when using the UFO model (it is aimed at stand-alone Sherpa, but since the Athena jobOption (JO) is basically the stand-alone configuration file plus extra Athena settings it can still be very helpful)
* (If applicable) A separate file that collects the UFO model's parameters (`param_<model_nam>.dat`), which is included in the configuration file with this line: `UFO_PARAM_CARD: param_<model_name>.dat`

The outsourcing of the parameters to a separate file is optional. It can make the JO file shorter and more clear. It also simplifies comparisons to MadGraph, since the `param_<model_nam>.dat` file can be identical to Madgraph's parameter card (which makes it easier to match the settings between the two generators). [This example JO](mc.Sh_30_SMEFTsim_example.py) includes a separate parameter card. 

If preferred, the parameter settings can be contained in the JO instead: Change `UFO_PARAM_CARD: param_<model_name>.dat` to `UFO_PARAMS: |` and insert the settings from the parameter card below (with an indentation).


## Generating Events using the compiled UFO model
As always in Sherpa_i, the event generation is steered using a jobOption (JO) file. A possible strategy for setting up the JO is to start with an existing Sherpa_i JO (without the UFO model) and to then alter it according to the new settings detailed in the `Sherpa_<model_name>.yaml` file produced by the compilation script. This directory includes an example JO for a commonly used UFO model as a starting point. 

Notably, the JO always needs to include the line  `MODEL: <model_name>`. Also, the compiled library and, if applicable, the file with the parameter settings need to be named as necessary extra files using `genSeq.Sherpa_i.ExtraFiles = ['libSherpa<model_name>.so', 'param_<model_name>.dat']`.

Make sure that your working directory contains the compiled model library (`libSherpa<model_name>.so`). The event generation can then be run using `Gen_tf.py` as usual.

## Known Issues and Words of Caution
* Sherpa's UFO interface only supports LO simulations right now. Models with NLO features can still be compiled and used, but the relevant NLO parameters will be set to zero automatically.
* At this point, not all UFO models contained in the [Madgraph models repository](https://gitlab.cern.ch/atlas-generators-team/MadGraphModels) can be compiled with Sherpa. The collection is also regularly updated and new models are included, which might not have been tested yet. You can check this [Gitlab issue](https://gitlab.com/sherpa-team/sherpa/-/issues/647) to check for models with known problems.

## Tips and Tricks
* If applicable, it can be a very useful cross-check to compare the SM limit of the UFO model to results obtained with Sherpa's built-in SM. This helps to ensure that all parameters are being used correctly and that any differences later on are actually BSM effects, and not just discrepancies in the settings.
* One example of a setting that is different when using some UFO models is the `Order` setting. It restricts the coupling order of the process calculation at the squared-amplitude level. This means that in the case of a contribution representing the interference between SM and BSM Feynman diagrams, the correct order might be `NP: 0.5` ("NP" for "New Physics"). Of course this is highly dependent on the model and the desired result. For more information on the `Order` setting in Sherpa, please see the [Sherpa manual's section on the topic](https://sherpa-team.gitlab.io/sherpa/v3.0.1/manual/parameters/processes.html#order).
* With the inclusion of the UFO model's parameters, there are now three places in which the particle masses and widths can be altered: the settings in the `PARTICLE_DATA` section of the JO have the highest priority, followed by the settings specified in the ATLAS Base Fragment, followed by the UFO model parameters. The log file `log.generate` includes a summary table of the particle data used in the integration.
* Sherpa's particle containers (e.g. `90` for leptons and `93` for jets) include only massless particles. If Sherpa does not find any diagrams for a process definition that should have possible diagrams, it is worth double checking the log file to see if the UFO settings include masses for particles that were intended to be massless.

## About the Example JO included in this directory
This directory contains a JO using the SMEFTsim UFO model (with more examples to be added later, hopefully). Here are a couple of comments about the example and the settings in it:

### New EFT operators with SMEFTsim
The example JO called [mc.Sh_30_SMEFTsim_example.py](mc.Sh_30_SMEFTsim_example.py) adds new operators to the SM Lagrangian through the use of a UFO model called SMEFTsim, specifically the ```SMEFTsim_topU3l_MwScheme_UFO``` variety (references: [Website](https://smeftsim.github.io/), [SMEFTsim package](https://arxiv.org/abs/1709.06492), [Practical Guide](https://arxiv.org/abs/2012.11343)). The example process chosen here is the production of a hadronically decaying W boson in association with up to three jets. One of  those jets is mandatory in order to enable a generation level cut on the transverse momentum of the W boson.

The ```Order``` setting restricts the coupling orders of the process at the amplitude-squared level. In this case, setting ```NP: 1``` allows for only diagrams with exactly one new physics vertex (often referred to as the "quadratic" contribution).
The UFO settings are contained in a separate parameter card ([param_SMEFTsim_topU3l_MwScheme_UFO.dat](param_SMEFTsim_topU3l_MwScheme_UFO.dat)) and specify that the Wilson coefficient for exactly one operator is set to a non-zero value.
